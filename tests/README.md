# Myrkr security-control tests

Executable test plan that measures how effective each implemented control is.
Full plan, rationale, scope, and results: [`docs/security-testing.md`](../docs/security-testing.md).

| File | What it does |
|------|--------------|
| `secsuite.py` | **Phase 1** — adversarial crypto/input tests against the shipping binary (GCM/WinZip-AES tamper matrices, salt/nonce uniqueness, path-traversal corpus, malformed-archive robustness, password policy). |
| `redteam.py` | **Phase 2** — drives the instrumented build's `redteam <case>` command to fault-inject each memory-safety control and assert it fastfails with the exact expected code. Requires `build.cmd dbg`. |
| `run.ps1` | Builds both variants and runs both phases end to end. |

```powershell
# from the repo root, inside a vcvars64 shell:
pwsh tests\run.ps1
```

Requires Python 3 with `pyzipper` and `cryptography`. Phase 1 takes a few
minutes (it runs Argon2id hundreds of times).

## Feature tests

Not part of `run.ps1` — each builds the binary variant it needs and is run on
its own, and each leaves a **test** build in `bin\`, so rebuild release
afterwards. They exist because five defects in the drag-and-drop work reached
the user rather than a test: all five built clean and passed every checker, and
what would have caught them was asserting what is *drawn* or reading the result
back through something that owes the feature nothing.

| File | What it asserts |
|------|-----------------|
| `droptest.ps1` | the window is a real OLE drop target - `IDropTarget` driven through its vtable with a genuine `IDataObject` |
| `prefixtest.ps1` | a drop lands in the selected folder, checked by extracting and looking at where the file went |
| `indicatortest.ps1` | the destination box is drawn on the row the drop will go to |
| `stagetest.ps1`, `stagedroptest.ps1` | the staged layout: dropping into a folder while an archive is still being built |
| `afterencrypttest.ps1` | the two ends of a right-drag, plus the double-click path. A right-drag gets the small progress window and never shows the main one; on success it takes everything down by itself; on a **failure** (forced with `--to` pointing at a file) it halts there with the details folded out and the error in them. And opening a container still gives a window you can work in, checked by dropping a file and reading the archive back with the CLI. Note `Edit()`: the details panel must be read with `WM_GETTEXT`, because cross-process `GetWindowTextW` returns an EDIT's *creation* text however often it is replaced |
| `estreamtest.ps1` | the drag-out `IStream` **and** `IDataObject` (`src/estream.asm`): every entry's stream open at once, read round robin, compared byte for byte against `myrkr decrypt`, then the same container again through `GetData`; the exact names a given selection is offered under (a nested file by its leaf, a folder with everything beneath it); a tamper in the tar padding, which a reader that stopped at the last content byte would report as success; and the same object again over WinZip-AES **zips**, which drag out by the opposite mechanism (buffered, not streamed - `docs/DRAG_OUT.md` §7), compared against `myrkr unzip` |
| `mkzip.py` | not a test - builds `estreamtest.ps1`'s zip fixtures with pyzipper: AES deflate, AES stored, and unencrypted, one per output path in `extract_zip_entry`. myrkr cannot write a WinZip-AES archive, which is the point: the fixture owes the code under test nothing |
| `shellexttest.ps1` | `myrkrshell.dll` answers `QueryContextMenu` **and returns**. Loads the real DLL, goes through `DllGetClassObject` to a real COM object, calls the verb through its vtable twice (a wrongly restored frame can return once by luck). Runs it in a **child process** on purpose: a smashed return address does not raise a catchable error, it ends the process, so the child's survival is itself one of the checks — a harness that died with the code under test could not report anything. Written after 1.0.40 shipped a raw prologue raised without its epilogue and took `explorer.exe` down on every right-drag |
| `menuicon.ps1` | the context-menu icon survives the trip into `myrkrshell.dll`: `rc.exe` embedded it, the resource id the DLL asks for is the one that is there, and `LoadImageW` returns a 32-bit DIB whose alpha is still **premultiplied**. Three separate ways for the icon to come out a grey box, none of them visible in a build log. It loads the DLL with `LOAD_LIBRARY_AS_DATAFILE`, so `DllMain` never runs and nothing is registered. (Whether the *asset* still matches `myrkr.ico` is the build's job — `tools/make_menu_bmp.py --check`.) |
| `manyfiles.ps1` | **count in == count out**, which nothing else asserted. 20,000 files with 90-character names through encrypt → list → decrypt. Written after a report of 76,286 files in and 16,780 out with no error: the index had a fixed 2 MiB ceiling and `idx_add` dropped every entry past it while the payload went on receiving them, and unpack is driven entirely by the index — so those files became ciphertext with nothing recording their offset, ordinal or name. Long names on purpose, so the ceiling is reached with thousands of files instead of tens of thousands. Run against the unfixed build it fails three ways: the listing admits it is incomplete, 15,767 of 20,000 are listed, and 4,233 never come back. A refusal is treated as correct behaviour *provided no container is produced* — what must never happen again is a container that is short and says nothing. It also covers **`verify`, in both directions** - intact containers must pass and tampered ones must fail - across single/compressed, single/stored and archive. Nothing tested `verify` at all before, and it was wrong for every single-file container, calling sound archives corrupt. A check that only asserted "intact says OK" would pass a verify that always says OK, which is the far more dangerous failure for an integrity tool, so the tamper half is the point |
| `volumetest.ps1` | a container split across volumes comes back whole (`docs/VOLUMES.md`). Splits 10 MiB at ~2 MB a part with `MYRKR_DBG_VOLBYTES`, then checks the parts are shaped as the format says (every one `MVOL`, exactly one marked final) and that the archive decrypts **from any member** — part 1 *and* a middle part, which is what proves a set is assembled from the part numbers in the headers rather than from the name it was handed. Contents are compared by SHA-256 per file, not counted. Finally it deletes the last part and requires the set to be **refused**: the final flag exists so that a missing tail cannot extract as a short archive, which is the 1.0.51 failure arriving through a different door |
| `greytest.ps1` | what "disabled" looks like, from both ends. A genuinely disabled button must grey (the password prompt's OK, which starts disabled with an empty box and enables on the first keystroke) and a button repainted **under a modal dialog** must not. The second half exists because 1.0.61 shipped a full-window repaint on the theory that `IsWindowEnabled` is false for every child of a disabled parent; it is not, it reports the window's own state, and the test asserts that directly — with the main window disabled and a dialog up, Exit reads enabled and paints white. It **forces** the repaint from outside, because nothing invalidates those buttons on their own, which is exactly why that theory was never testable. Three earlier versions of it were discarded for passing against a build with the fix removed: comparing two buttons with different labels, diffing whole button faces, and sleeping instead of waiting for the surface to settle |
| `counttest.ps1` | the numbers on screen reconcile with Explorer. Reported as "84079 files, 309 B" for a 587 GB folder of 76,286 files and 7,792 folders — two faults on one line. The count was index **entries** (76286 + 7792 + 1 root = 84079 exactly) while calling them files, which also drove the progress window's numerator past its denominator ("84000 of 76286 files"), the numerator being the action log's tally of entries. And the byte total was accumulated inside the row walk *after* the check that skips collapsed rows, so a container — which opens with its folders shut — reported whatever sat at its top level and changed as folders were opened. The fixture puts nearly every byte two levels down, so a visible-only total misses them; without that nesting it passes against the broken build. Mutation-checked: the old code reports "5 files, 309 B" for 2 files, 3 folders and 5,000,309 bytes |
| `extracttest.ps1` | extraction goes straight from the inventory to the files, with nothing in between (`docs/V5_WORK.md` step A2). Until 1.0.71 a decrypt of an archive wrote a **complete decrypted copy of it** to a temporary file beside the container and then walked that back — 3N of I/O, N of scratch, and a second full plaintext on disk for the length of the run. Two claims, both easy to lose silently. **No scratch**, proved by `icacls`-denying this process the right to create files in the container's own directory and requiring the decrypt to succeed anyway — not by watching for a temp file to appear, which is a race. And **a tampered entry never reaches disk**: a flipped byte inside one entry must fail the run, must leave nothing of that entry behind, must leave only byte-identical files from the entries before it, and must SAY the extraction is incomplete — a short folder full of authentic files reads as a partial success and is not one. Runs stored and compressed, and covers the single-file case, where the output is written as `.part` and renamed only once its tag verifies. Mutation-checked five ways; the list, including the one that failed differently from how it was predicted to, is at the bottom of the file |
| `optiontest.ps1` | an argument that looks like an option and is not one must be **refused**, not turned into an input path. Found in the 1.0.71 audit: the option collector fell through to "this is a positional" for anything it did not recognise, so `--stor` (for `--store`) named a file. If no such file existed the run died with `error: I/O failure`, which blames the disk for a typo and names nothing; **if one did exist the run exited 0**, silently ignoring the option and putting that file in the archive. Checks both shapes, plus the two things the fix must not break — an option *value* beginning with `-` (a dash-leading password) and `.\-name` for a file whose name really does begin with `-`. Mutation-checked; the note records two corrections to itself, including a first version of the exit-0 check that could not fail because the decoy file was one directory off |
| `compattest.ps1` | containers written by an OLDER Myrkr still open. Every reader compares the header version for exact equality, so a bump makes every existing container read as "not a valid Myrkr container" — the tool calling intact data damaged. Phase B (`docs/V5_WORK.md`) bumps it, and the fixture that proves compatibility **cannot be made after the bump**, so `tests/fixtures/v6-*.mrk` were frozen at 1.0.72 and are **never regenerated** (`tools/make_v6_fixtures.ps1` is provenance and refuses to run). Five containers — archive stored and compressed, bare stored and compressed, a three-part volume set — opened, hashed file by file, listed and verified. It also asserts their **on-disk version byte**, because a fixture regenerated by a newer writer would still decrypt and this test would pass while proving nothing. Plus both directions of the wording: another format version says so and says the file is not damaged; a corrupt one still says corrupt. Mutation-checked with `HDR_VERSION 6 -> 7`, the exact change phase B makes |
| `segmenttest.ps1` | a large entry is a run of GCM streams - segments - and both ends keep their word (`docs/V5_WORK.md` B4-B6). Round trip, verify and the **drag path** at 64 KiB segments (`MYRKR_DBG_SEGBYTES` shrinks the 4 GiB default - ON since 1.0.83), stored and compressed, including the boundary-exact entry the lazy roll exists for; tampers in a middle segment, a segment tag and the tail; truncation; hostile `seg_shift` values (63 would be 2^63, 64 would quietly compute `1<<0` - `shl` masks to 6 bits). The check the file exists for is the **nonce log**: test builds log every nonce built, and the test asserts all distinct and (stored mode) exactly the sum of per-entry segment counts plus the index. Mutation 1 is why - delete the segment increment from BOTH the writer's roll and the reader's reopen and every content check passes while 10 of 18 nonces are duplicates; a writer and reader that repeat a nonce in step agree with each other perfectly, and only the log of what was issued can see it |
| `progresstest.ps1` | the bar tells the truth about time: cumulative-average MB/s and a ticking eta, requested after a 155 GB encrypt left a bar with no schedule. The clock starts at the FIRST BYTE (the KDF's head would drag the average down), the eta CEILS (a moving bar must never read 0:00 - the shipped first draft did, at 59%, arithmetically true and misleading anyway), and the bar aims at the CONSOLE by design, which made it invisible to every harness until `MYRKR_DBG_PROGRESS` (test builds) rendered it into the captured real stderr. Asserts the line's shape, a plausible rate band, 0:00 only at 100%, a falling eta, and that WITHOUT the override a redirected stderr still gets nothing. The arithmetic itself - the 128-bit remaining*elapsed product, the 99:59:59 cap, the gates - is a selftest case with injected state. Mutation-checked both ways |
| `indexfulltest.ps1` | the inventory-full refusal, reached with **forty files instead of half a million**. It is the fix for the worst failure this project has had - 76,286 files encrypted, 16,780 recorded, exit 0, the rest unaddressable ciphertext - and nothing had ever exercised it, because the ceiling is 64 MiB of index (~500,000 entries). `MYRKR_DBG_IDXMAX` lowers the limit the WRITER applies; the reader's bounds stay pinned to `IDX_MAX_BYTES`, since a knob that loosened those would be a buffer overflow with a switch on it (`idx_cap`, pack.asm). Checks the refusal, its message, that **no container is left behind**, that the same inputs pack fine at the default limit, that a nonsense cap is ignored rather than obeyed, and that a tiny writer cap does not stop a good container being read. Mutation 1 restores the pre-1.0.51 behaviour and reproduces the disaster in miniature: exit 0, container present, 12 of 40 files listed |
| `scaletest.ps1` | **not in the default suite** - it builds half a million files and takes minutes; run it deliberately. 89-character leaves at ~137 bytes an entry, so the inventory is 68.5 MB: larger than the whole 64 MiB ceiling that existed before 1.0.81, i.e. a container this tool could not previously have produced. Times and measures the commit of encrypt, list, verify, add and decrypt. A first version asked for 200-character leaves and was correctly refused - ustar bounds the leaf at 100 bytes - which is why the arithmetic is spelled out in the file. What it found: `list` takes 509 s against `verify`'s 2.6 s for the same index, because `do_list` prints five fragments an entry and each is an unbuffered `WriteFile` - 2.5 million syscalls. See `docs/V5_WORK.md` |
| `canceltest.ps1`, `pickertest.ps1`, `rmbartest.ps1`, `threadtest.ps1` | cancellation, the folder picker, the removal progress bar, worker-thread safety |

One thing here has **no** automated test and is verified by using it: the drag
*out* of a container — `LVN_BEGINDRAG` → `DoDragDrop` → Explorer's copy loop.
`docs/UI_SURFACES.md` records four attempts at driving a drag and why the last
one cannot work (`DoDragDrop`'s `SetCapture` only takes effect for the
foreground thread). The objects either side of it are covered by
`estreamtest.ps1`; see `docs/DRAG_OUT.md` §4e for exactly what is left
uncovered and how much logic that is.
