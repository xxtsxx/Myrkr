# Security review, 2026-09-04

Baseline: `afb916c6986c61adef74f6163c22cae721e3564d`.

This is a targeted source review with deterministic reproductions. It does not
establish that every assembly instruction is correct. The earlier broad test
pass and "no release blocker" assessment did not cover the flaw below.

## High: copied containers reuse GCM nonces when edited (fixed by full re-encryption)

The previous `do_add` restored the existing key and authenticated `IDXT_next` from the file.
`entry_begin` uses that ordinal; `entry_stream_open` constructs the nonce as
ordinal + 1 and segment number. Index encryption likewise derives its nonce
from an in-file revision. Copies of a container therefore inherit identical key
and nonce-allocation state. Authentication of the counters does not make that
state unique across copies or restored backups.

Originally reproduced with `tests/nonceforktest.py` against the unmitigated
`build testio` binary (the test now asserts fresh-key edits):

1. Encrypt a synthetic seed file with compression disabled.
2. Copy that container to two independent paths.
3. Append 64 `A` bytes to one and 64 `B` bytes to the other.
4. Both containers pass `verify`.
5. XOR the appended ciphertext at the same content offset: every byte is 3,
   exactly `A XOR B`. Known plaintext in one copy recovers the other payload.

An observer needs both resulting ciphertexts. No password is needed to compute
their XOR. This is a confidentiality failure, not merely acceptance of an old
container. GCM authentication assurance also depends on nonce uniqueness; this
reproducer proves keystream reuse, not a complete tag-forgery exploit.

The same state-management concern applies to restored versions and counters
rolled back after aborted writes if the abandoned ciphertext is observable.
Those variants have not been separately reproduced here.

A durable remedy must make edits safe across independent copies. Options include
rewriting under a fresh key on every edit, or a versioned format with independently
randomized per-write key/nonce domains for entries AND inventory rewrites. Merely
increasing or authenticating the existing counters cannot solve forks.

### Implemented remedy

Every native add/removal now uses `native_rewrite`; the in-place mutation
implementations have been removed. It snapshots the authenticated index/key,
opens a source handle that excludes concurrent writers, and rechecks the
authenticated header and index tag/trailer after obtaining that handle.
The decoder owns its source header/key across segment boundaries.

All source entries, including removals, are authenticated. Survivors are streamed
through the normal entry writer into a randomly named sibling created with
CREATE_NEW. The replacement receives a fresh 32-byte salt, 12-byte identity, and
Argon2id-derived key using the original password and KDF costs. Compression and
segmentation policy are preserved; output is version 8 with fresh ordinal and
revision counters. An empty inventory retains the minimum payload tag required
by existing readers.

Disk-space preflight is conservative; every write remains checked. The output
is flushed and closed before `ReplaceFileW`, while the source's writer-exclusion
handle remains open. Cancellation and pre-commit failures remove only this
operation's temporary file, leaving the original unchanged. On a replacement
failure, Windows can already have removed the original name: the completed
encrypted temp is therefore kept, `EXIT_PARTIAL` returned, and its recovery
path reported (including a GUI dialog). Filesystem/power-loss durability beyond
the operating system's guarantees is not claimed. Old ciphertext in backups,
snapshots, or storage remnants is not securely erased.

The GUI warns at 100 MiB of container bytes, decoded content, or an added input,
and native removal now has a Cancel button. An early cancel is retained across
progress initialization. ZIP editing remains separate; volume edits remain
unsupported.

`nonceforktest.py` checks independent fresh salts, stored/compressed add/delete
readback, duplicate/missing-input rollback, and corrupted-source refusal.
`nativeeditguitest.ps1` checks successful small removal, the large-file warning,
declining it, and cancelling a removal. Both run in `tests/run.ps1`.
Existing exposure from older binaries cannot be undone by this patch.


## ZIP64 record bounds (fixed in working tree)

`extract_zip_entry` bounded the overall extra area, but read ZIP64 replacement
fields without checking the selected record's declared payload length. A record
declaring zero bytes could supply three 64-bit values from the bytes after it.
Eight malformed length variants were accepted with exit 0 before the fix.
Depending on layout, this also permits reads outside the declared extra record;
no exploitable process-memory disclosure or crash is claimed by these fixtures.

The parser now checks the complete extra record against the containing area and
requires eight remaining bytes before each replacement-field read.

## ZIP filename truncation (fixed in working tree)

The extractor converted length-delimited ZIP filenames to NUL-terminated strings
without rejecting embedded NULs, and clipped names longer than 4094 bytes. This
could extract under a different name, including overwriting an existing file
with that shortened name. Both cases are now rejected before output is opened.

`tests/zipboundstest.py` includes valid ordinary and ZIP64 controls plus malformed
lengths, an embedded NUL, and an oversized name. All 12 cases pass after the fix;
the initial nine malformed fixtures were accepted before the fix.

## Additional open review areas

- Extraction uses textual name sanitization and ordinary path-based opens.
  Existing junctions/reparse points in the destination need a dedicated escape
  test and a handle-based containment design; no dynamic reproduction was run.
- Power-loss and filesystem-failure recovery need broader fault-injection
  coverage. Native edits no longer append in place; ZIP has separate edit paths.
- Secret-memory locking is best-effort. Transient GCM contexts and the Argon2
  arena are explicitly excluded from locking in `secmem.asm`. Blanket statements
  that all secrets are non-pageable exceed what the implementation guarantees.

The ZIP fixes do not resolve these areas. The nonce flaw is addressed by the fresh-key rewrite described above; this is not a claim of a complete security audit.
